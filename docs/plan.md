## 后端方案（2026-10-15 合并）

来源：用户对项目 PDF、评审建议及后端 Agent 设计的讨论与修正，由 OpenCode 辅助整理。**Python + LiteLLM、优先使用 Lexmount Python SDK 和轻量架构是用户明确的技术方向；以下接口、文件划分与默认参数是实现建议，尚未编码或验证。**

### 1. 范围与架构

先打通 R0 画像 → R1 粗筛 → R2 精查 → R4 路线的闭环。首轮建议深度验证 30–50 个代表性竞赛实例，不等待全部历史记录补全；这不限制采集侧保存更多原始记录。

R3 六角色讨论、实时插话、复杂权重滑块不是首版依赖。`.ics` 导出和在线补全放在主线之后；是否列为提交必需项仍按 `issue.md` #2 决定，不因本方案列出接口而视为已经定案。

```text
前端（独立开发）
  │ HTTP / JSON
  ▼
FastAPI（单个 Python 进程）
  ├── Agent：LiteLLM 调用模型
  ├── Tools：竞赛查询、证据读取、资格和时间检查
  ├── Lexmount Python SDK：按需获取网页资料
  └── 本地文件：竞赛 JSON、私有会话 JSON
```

- LiteLLM 作为 Python 库直接调用，不部署 LiteLLM Proxy；默认接入原方案的 DeepSeek，模型名和凭据通过配置提供。
- 首版不使用数据库。确有持久化查询或并发写入需求时再考虑 SQLite，而不是预先引入 PostgreSQL。
- 请求内完成对话和有限次工具调用；耗时采集尽量提前执行，不搭建后台任务系统。
- 普通 HTTP 返回完整结果即可，流式输出按实际前端需求增加，不默认依赖 SSE 或 WebSocket。
- 前后端分离指 HTTP 契约和独立开发，不要求分别部署到不同服务器。

### 2. 建议目录

```text
backend/
  main.py          # FastAPI 路由、请求处理
  agent.py         # 提示词、上下文、LiteLLM 工具调用循环
  tools.py         # 领域工具定义、参数校验、调用分发
  collector.py     # Lexmount Python SDK、网页资料清洗
  schemas.py       # Pydantic 请求、会话与结果结构
  storage.py       # 本地文件读写
  tests/           # 资格、时间、工具循环和接口测试
data/              # 沿用已有忽略规则，不提交真实数据
  competitions.json
  sessions/
```

以上是拟新增结构；现有 `lib/`、`collect/`、`scripts/` 继续作为采集与探索工具保留。不要为了统一语言重写已经可用的采集代码。

### 3. 一个 Agent，按阶段切换模式

| 阶段 | 模型负责 | Python 代码负责 |
|---|---|---|
| R0 画像 | 提取用户信息、追问、提出画像修改草案 | 字段校验、保存草案、接收用户确认 |
| R1 粗筛 | 领域相关性、候选理由 | 资格与报名时间检查、记录保留/排除/恢复 |
| R2 精查 | 基于证据分析能力差距、目标价值和风险 | 查询资料、按需补全、校验证据引用 |
| R4 路线 | 提出所选竞赛的任务和时间安排 | 计算每周投入、检查日期冲突、可选日历导出 |

- 用户确认后才进入下一阶段，模型不能自行跳过确认。
- 不必先搭建状态机框架；会话只保存当前阶段、相关消息、画像草案与确认版本、候选、用户决策和当前结果。
- 用户修改画像后，旧分析标记为待更新；同一会话内串行处理修改，防止并发请求覆盖新状态。
- 模型不直接执行任意代码、SQL 或写文件；持久化和阶段切换由后端控制。

### 4. LiteLLM 工具循环

```text
读取会话与阶段
  → 组装阶段提示词、已确认画像、相关候选与证据
  → LiteLLM 调用模型
      ├── 工具调用：校验名称和参数 → 执行 → 结果回传模型
      └── 最终草案：Pydantic 校验 → 引用和业务检查 → 保存并返回
```

- 每次请求建议最多 5 轮模型调用，同时限制工具数量，并设置模型和网页访问超时；具体值通过实测调整。
- R0 通常只需一次结构化调用；R1 的硬条件由代码批量执行，不必让模型逐条调用工具。
- 工具输出保留状态、数据、证据和警告；超时或失败不能解释成「没有竞赛」。
- 输出解析失败只做有限次修复；超过预算向前端返回明确失败或信息不足，不无限重试。
- 工具调用超时、配额、结构化输出和 Lexmount SDK 的具体接口需在实现时做小样验证，本方案不假设已经跑通。

建议工具仅包括：

| 工具 | 作用 |
|---|---|
| `search_competitions` | 按领域、年度和报名状态查询本地数据 |
| `get_competition` | 读取实例、通知、资格和赛程 |
| `get_evidence` | 读取允许访问的来源摘录 |
| `supplement_competition` | 用 Lexmount SDK 补充指定实例的缺失字段，设置缓存和超时 |
| `check_eligibility` | 返回明确符合、明确冲突、信息不足及依据 |
| `check_plan_feasibility` | 检查每周投入、日期冲突和待核实信息 |

### 5. 数据与可信性

不需要关系型数据库，但 JSON 内仍需区分 **竞赛系列 → 年度/届次 → 赛区/组别/阶段 → 通知/报名记录**，用稳定 ID 关联，不能只按名字合并或删除记录。

- 报名状态区分正在报名、尚未开放、已截止、时间未知；往年日期不充当今年确定日期。
- R1 只有明确冲突才能硬性排除；因展示数量或相关性暂不展示的候选另行标记，允许恢复。
- 每个重要结论关联证据 ID；证据保存摘录、URL、读取时间、适用年度和组别，浏览器采集时附 session ID。
- 区分官方明确说明、根据材料推断、信息不足；引用存在不等于结论成立，仍需规则检查和人工抽检。
- 无数据时不输出获奖概率；改为准备难度和风险。保研价值以适用学院、年级的正式政策为依据，不能直接由 A/B 类推导。
- 路线写成「任务 + 预计投入 + 验收标准 + 时间范围 + 假设」，检查总投入而非只看单项竞赛。未知日期不导出为确定日历事件。
- 推荐卡片和路线保存为结构化数据，不只保存 Markdown；模型上下文只加载当前需要的资料，不反复发送全部历史网页。

### 6. 采集与安全

- 默认采用「提前采集 → 清洗 → 人工抽检 → 保存本地 JSON」，保证 Demo 不依赖现场完整抓取。
- 需要时再在线调用 Lexmount Python SDK 补全少量资料；SDK 接入集中在 `collector.py`，具体版本和方法实现时核实。
- MIS 当前默认公网直连，隧道可选，沿用现有实测结论；登录流程和验证码仍按 `issue.md` #1 单独处理，不把旧 PDF 的 VPN 假设带回实现。
- 复用现有私有配置的存放约定，Python 侧的读取方式及模型 key 配置项在实现时确定；不生成或记录真实凭据。
- 账号、Cookie、`connectUrl`、`inspectUrl` 不传入模型或写入会话文件；登录不开录制，失败不自动反复尝试。
- SDK 会话在 `finally` 中关闭，先关闭会话再关闭隧道；不默认并发抓取 MIS。
- 外部网页只作为资料，不作为操作指令；工具限制 URL、目标范围、文件类型和大小，不开放任意地址访问。
- 校内数据云端处理需确认许可，只读不自动代表允许上传；真实竞赛资料和用户会话继续放在被忽略的 `data/` 中，不公开原始全集。
- 本地 JSON 按会话分文件、串行修改并采用原子替换，避免中断留下半文件；首版仅按单进程小规模试用设计，不承诺跨进程恢复执行。
- Demo 默认仅本机访问；若向其他同学开放网络访问，需先补充会话归属校验和必要的访问控制，不能只凭可猜测 ID 读取会话。

### 7. 前端接口契约（建议）

| 接口 | 用途 |
|---|---|
| `POST /sessions` | 创建推荐会话 |
| `GET /sessions/{id}` | 恢复当前阶段和结果 |
| `POST /sessions/{id}/chat` | 对话或生成当前阶段草案 |
| `PATCH /sessions/{id}/profile` | 用户修改画像，标记受影响结果待更新 |
| `POST /sessions/{id}/confirm` | 确认当前草案并推进阶段 |
| `PATCH /sessions/{id}/candidates/{candidate_id}` | 保留、排除、恢复候选 |
| `GET /competitions/{id}` | 查看实例和证据 |
| `GET /sessions/{id}/calendar.ics` | 可选：导出已确认日期 |

聊天成功响应统一包含 `message`、`stage`、`profile`、`cards`、`needs_confirmation`；失败返回稳定的错误码和可读说明，不回传包含凭据的底层异常。前端负责展示和编辑，不持有模型或 Lexmount key。

本次只确认后端方向，不指定前端框架，也不把旧方案的 `web/server.mjs` 继续作为前端依赖。

### 8. 开发与验证顺序

1. 少量审核后的本地竞赛数据 → FastAPI + LiteLLM 画像对话。
2. 查询工具 → 带证据推荐卡片 → 用户修改和确认。
3. 路线生成 → Python 检查资格、每周工时和日期冲突。
4. 接入 Lexmount Python SDK 补全；根据 MVP 决策再增加 `.ics` 或流式响应。
5. 验证完整闭环、刷新恢复、工具失败、输出格式错误、重复请求和用户纠正。

资格与日期规则用固定数据测试；模型和浏览器调用可替换为测试返回值。另保留少量真实 LiteLLM / SDK 集成测试，人工抽检 30 条并开展 3–5 人试用，不把测试替身通过当作外部接口已验证。

## 原方案（历史记录，与上方冲突处以上方为准）

原方案头注：截止 2026-10-25 23:59，计划 10-24 提交；团队 2–3 人。

## Context

北交大教学支撑平台（`aa.bjtu.edu.cn`）的「竞赛项目」页有 700 多条竞赛，分属不同学院，技能要求各不相同。学生难以判断自己适合参加哪些。

目标：Agent 通过对话逐步问出用户的能力和偏好，结合 MIS 竞赛数据与公开信息，评估能力差距，和用户讨论后给出参赛方案（推荐竞赛 + 备赛路线 + 时间线），以网页 Demo 交付。

约束：
- MIS 只能经客户端 VPN 访问；登录需要统一身份认证和算术验证码。
- 竞赛信息基本只在 MIS 上。

## 主办方工具的使用映射

| Lexmount 能力 | 用在哪里 | 作用 |
|---|---|---|
| CloudBrowser + **本地隧道** | MIS 采集 | 在不暴露内网的前提下让云浏览器访问 VPN 内系统 |
| **持久化 Context + fork** | 登录一次，fork 出多个已登录的 context | 并发抓取 700 条详情（Pro 25 并发），不用反复登录 |
| **Session 下载存储** | MIS 详情页附件、官网章程 PDF/Word | 取回本地后解析知识要求和赛程 |
| **WebFetch** | 静态官网和通知页批量读取 | 快、便宜；读取失败再升级到 CloudBrowser（分层抓取） |
| CloudBrowser（normal / light Moli） | 搜索引擎、JS 渲染的官网；简单页面试用 light 模式 | 处理需要交互的页面；light 模式的成本和效果待验证 |
| **录制回放 + 会话记录** | 所有云端会话 | 「过程可信」的证据，Demo 录屏也可以引用 |
| Agent 实时调用 | 讨论阶段核实争议点（如「今年还办吗」「去年什么题型」） | 让 Agent 的结论有现场证据 |
| CLI + Skill | 队友的 Apple Silicon / Windows 机器上，用 Claude Code + Skill 先手动探索 MIS 和官网结构 | 提高开发效率；投稿中作为「工具分工」写进去 |

- 不使用：官方代理（不用来规避站点规则）、自动验证码处理（MIS 走人工弹窗登录）。
- WebFetch 和 Moli 的具体接口与额度，第一天确认。

## 架构：Lexmount 全程参与

| 阶段 | 做法 | Lexmount 角色 |
|---|---|---|
| 1. MIS 采集 | 本机连 VPN → `client.tunnels.open()` 打开本地隧道 → 云浏览器经隧道访问 MIS | 云浏览器 + 本地隧道（SDK 0.6 官方能力，`node_modules/lexmount/README.md`「Access a company network」） |
| 2. 公开信息补全 | 云浏览器在必应搜索竞赛名 → 打开官网、往届通知、获奖公示 → DeepSeek 抽取知识要求、难度证据、赛程 | 云浏览器（不走隧道） |
| 3. Agent 对话与评估 | DeepSeek 多轮对话 + 工具调用；可在对话中实时触发云端搜索 | Demo 中现场调用 |

**弹窗登录**：
- 脚本创建会话后，在本机浏览器打开该会话的 `inspectUrl`（SDK `SessionInfo.inspectUrl`）。
- 用户在弹出的窗口里手动输入账号、密码和验证码。
- 脚本检测到跳转进 MIS 后接管。
- 登录态存进 Lexmount 持久化 context（`contexts.create` + `mode: 'readWrite'`），后续会话复用，减少重复登录。
- 凭据不写入任何文件或脚本。

**过程证据**：每个会话开启 `recording: { persistent: true }`；每条数据记录 session ID、URL 和读取时间。`connectUrl` 和 `inspectUrl` 能接管会话，不写进日志。

## 数据

**MIS 原始记录**（`data/mis-raw.jsonl`）：
- 列表字段：年度、项目编号、名称、级别（国际/国家/省部/校级）、类型（A/B/C）、轮次、报名时间。
- 详情页：「查看」后的全文。
- 负责人姓名不保存。

**竞赛去重**：700 条包含往年、多轮次、多赛区。按名称归一化后得到「竞赛」实体，再按报名时间筛出近期的。

**竞赛画像**（`data/competitions.json`）：
- 知识/技能要求标签（含程度）、形式（个人/组队、线上/线下）、赛程。
- 难度证据（往届题型、获奖比例等）和重要性证据（MIS 级别与类型、是否在全国竞赛目录内）。
- 每条附来源 URL；缺失的标「未说明」。
- **补全优先级**：近 6 个月可报名的 → A/B 类 → 其余（受 Browser hours 额度限制）。

## Agent 设计：多轮筛选 + 用户 review + 多 Agent 讨论

原则：
- 权重不是固定公式，而是「Agent 提出草案 → 用户 review → 根据反馈修正」。
- 规则只负责硬性条件和日期；其余维度用「档位 + 证据 + 置信度」表示，不压成一个分数。

**R0 画像访谈**（访谈 Agent）
- 从自由文本开始，逐步追问：年级与专业、技能及其证据（课程/项目/获奖）、每周可投入时间。
- 再问目标偏好：保研、简历、兴趣、奖金，个人还是组队，倾向的领域。
- 输出画像 + **初始权重草案**（附理由，例如「你提到保研，所以 A 类权重高」）。
- 用户 review：在侧栏直接修改，或用一句话纠正。

**R1 粗筛**（700 → 约 40）
- 硬条件：报名窗口、年级/学院限制。只在明确冲突时剔除。
- 领域相关：模型做宽松的语义匹配，宁可多留。
- 按领域分组展示，每条一句入选理由。
- 用户 review：保留、剔除、补充（「我也想看看数模类」）。被剔除的可以恢复。

**R2 精查**（约 40 → 10–15）
- 对候选实时调用 Lexmount（先 WebFetch，不行再用 CloudBrowser）补全公开信息。
- 每个竞赛生成多维评分卡，每维给出档位、证据链接和置信度：
  - 能力差距（按知识标签逐项）
  - 对用户目标的价值（MIS 级别/类型 + 公开认可度）
  - 时间成本 vs 可投入时间
  - 获奖可能
  - 赛程冲突
  - 组队需求
- 权重来自 R0 的草案，用户可用滑块或自然语言调整（「我更在乎能不能拿奖」）。
- **稳健性提示**：标出哪些竞赛在不同权重下都靠前（稳健推荐），哪些只在特定权重下靠前（看偏好）。
- 用户反馈（「这个太难」）会同时更新画像和权重，不只影响单条。

**R3 多 Agent 讨论**（10–15 → 2–3 套组合方案）
- 角色（用户可勾选参与讨论的角色）：
  - **能力教练**：差距能否在比赛前补上，怎么补
  - **收益分析师**：对用户目标的价值，级别与认可度
  - **时间规划师**：与课程、考试、其他比赛的冲突和总工作量
  - **学长学姐**：从公开经验帖和往届获奖情况出发发言，依赖 `web_lookup`
  - **质疑者**：挑战乐观假设、找证据缺口，必要时调 `web_lookup` 现场核实
  - **主持人**：汇总意见，必选
  - 预设「精简模式」：支持方 + 质疑者 + 主持人
- 流程：各自独立发表意见 → 交叉回应 1–2 轮 → 主持人综合成「稳妥型 / 冲刺型 / 探索型」组合，标注仍有分歧的点。
- 用户参与：
  - 讨论通过流式输出实时展示，用户旁听。
  - **用户可以随时插话**：消息进入队列，在下一位 Agent 发言前注入上下文，主持人负责回应或转交给相关角色。
  - 结束后用户 review 摘要（可展开全文），选定一套方案，或加约束（「下学期课多」）后重新讨论。

**R4 最终方案**
- 选定的竞赛及理由（附证据链接）。
- 备赛路线：针对每个差距，列出学什么、练什么、用什么资源、达到什么里程碑。
- 时间线：从报名截止日和比赛日倒推，可导出 `.ics` 日历。

**工具**（DeepSeek function calling）：
- `update_profile`、`update_weights`
- `search_competitions`、`get_competition`
- `web_lookup`：Lexmount WebFetch / CloudBrowser 实时查询
- `hard_filter`：确定性规则
- `scorecard`
- `make_plan`
- 每轮的输入、输出和用户反馈都写入会话日志，作为可复查的过程材料。

## 代码结构（Node，复用现有 `lexmount`、`playwright`、`dotenv`，不新增依赖）

- `lib/lexmount.mjs`：`withTunnel(fn)`、`withCloudSession(opts, fn)`，沿用 `scripts/smoke-test.mjs` 的 try/finally 关闭顺序（先 session，后 tunnel）。
- `lib/deepseek.mjs`：通过 `fetch` 调用 OpenAI 兼容接口（含 tools）。
- `collect/mis.mjs`：弹窗登录后，从持久化 context fork 出多个会话，并发遍历「竞赛项目」列表、详情和附件；限速，只读，不点「报名」。
- `enrich/fetch.mjs`：分层抓取（WebFetch → CloudBrowser），必应搜索 + 官网和章程抽取，带缓存。
- `agent/rounds/`：`r0-interview`、`r1-coarse`、`r2-scorecard`、`r3-debate`、`r4-plan`
- `agent/roles/`：教练、收益、规划、学长学姐、质疑、主持人的提示词
- `web/server.mjs` 用 SSE 推送讨论流；用户插话通过 POST 进入讨论队列
- `agent/tools.mjs`、`agent/filter.mjs`（硬条件和日期）
- `web/server.mjs`（Node 原生 `http`）、`web/index.html`：聊天区 + 画像/权重侧栏 + 每轮 review 面板 + 讨论记录 + 最终方案
- `lexmount-config.yaml` 增加 DeepSeek key（键名待定）；`data/` 不公开。

## 时间线与分工（A 采集/云端，B Agent/评分，C Demo/材料/用户测试）

范围优先级：先打通 R0→R1→R2→R4 主线；R3 多 Agent 讨论和插话第二周接入。如果时间不够，R3 先只做精简模式。

**批准后的第一步（由我来做）**：写 `lib/lexmount.mjs` 和 `collect/mis.mjs --pages 1`。你连上 VPN 后运行，在弹窗里登录，验证隧道、`inspectUrl` 交互和持久化 context 三件事。

- **10-14 决策门槛**：
  - A：隧道可用（需要项目开通 `custom_proxy` 权限）。
  - A：`inspectUrl` 弹窗登录成功，持久化 context 能保住登录态。
  - A：采到 1 页「竞赛项目」。
  - A：云端必应搜索跑通 1 个竞赛。
  - B：DeepSeek 工具调用跑通。
  - C：用活动页报名领取 Pro；登录投稿页查看表单字段。
- **失败兜底**：
  - 隧道权限未开：邮件 support@lexmount.cn 申请；期间先用本地 Playwright 采集 MIS，云端只做补全。
  - `inspectUrl` 不能交互：改为截图验证码，由用户在终端输入答案。
- **10-15～16**：全量采集 + 去重（A）；评分规则和画像结构（B）。

## 合规与安全

- 只用本人账号，只读、低频访问；Agent 不执行报名操作。
- 公开材料中给负责人和学生姓名打码，不公开 MIS 原始数据全集。
- 用户描述只发给 DeepSeek，不公开。
