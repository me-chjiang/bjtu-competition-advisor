# 北交大竞赛能力匹配 Agent：项目简述与方案

> AI 辅助生成（Claude），方案草稿，待团队确认。

## 1. 一句话介绍

一个对话式 Agent：通过问答了解学生的能力与目标，从校内 700 多条竞赛中筛出适合的几项，并给出备赛路线和时间线。竞赛信息由 Lexmount 云浏览器采集（计划）。

**项目简述**
- **为谁**：北京交通大学在校学生，尤其是不清楚自己适合参加哪些竞赛的同学。
- **解决什么**：竞赛信息只在校内教务系统（MIS）上，共 700 多条，分属不同学院、技能要求各不相同，学生难以判断。
- **产出什么**：网页 Demo（计划）：推荐竞赛及理由、备赛路线、可导出的时间线（`.ics`）。

## 2. 问题与用户

- **信息量大且分散**：700 多条记录包含往年、多轮次、多赛区，同一竞赛会重复出现。
- **信息难访问**：MIS 只能经校内 VPN 访问，登录需要统一身份认证和验证码。
- **判断成本高**：学生需要同时看清三件事：自己的技能与竞赛要求是否匹配，参赛对目标（保研、简历、兴趣、奖金）是否有价值，时间是否冲突。
- **目标用户**：在校学生，可单人或组队参赛。

## 3. 方案总览

### 数据怎么来

1. **MIS 采集（计划）**：用户本机连接校内 VPN，通过 Lexmount 本地隧道让云浏览器访问 MIS。用户在弹窗中手动完成登录；登录态保存到 Lexmount 持久化 context，之后并发 fork 出多个会话，遍历列表与详情页。只读，不执行报名。
2. **云端补全（计划）**：云浏览器（不经隧道）搜索竞赛名，打开官网、往届通知和获奖公示，抽取知识要求、难度证据和赛程。每条信息附来源 URL；取不到的标「未说明」。
3. **去重与优先级**：按名称归一化得到「竞赛」实体，再筛出近期可报名的；补全顺序为近期可报名 → A/B 类 → 其余。

### Agent 怎么用

- **多轮筛选 R0–R4**（见第 5 节）：每轮 Agent 给出草案，用户可修改后进入下一轮。
- **R3 多 Agent 讨论（计划）**：能力教练、收益分析师、时间规划师、学长学姐、质疑者、主持人共 6 个角色讨论；用户可旁听、勾选参与角色，并随时插话，插话在下一位发言前注入上下文。
- **设计原则**：权重不是固定公式，而是「Agent 提草案 → 用户修正」。规则只处理硬性条件（报名窗口、年级限制）；其余维度用「档位 + 证据 + 置信度」表示，不压缩成一个总分。

## 5. 多轮筛选流程

- **R0 画像访谈**：输入自由文本。Agent 逐步追问年级专业、技能及其证据（课程、项目、获奖）、每周可投入时间、目标偏好。输出画像和初始权重草案（附理由）。用户在侧栏修改或用一句话纠正。
- **R1 粗筛**（约 700 → 约 40）：输入画像和竞赛列表。规则只剔除明确冲突的项（报名窗口、年级/学院限制），领域匹配宽松、宁可多留。输出按领域分组、每条一句入选理由。用户保留、剔除或补充；被剔除的可恢复。
- **R2 精查**（约 40 → 10–15）：输入候选竞赛。实时调用 Lexmount 补全公开信息（先 WebFetch，失败再用云浏览器）。输出多维评分卡：能力差距、目标价值、时间成本、获奖可能、赛程冲突、组队需求。每维给出档位、证据链接和置信度，并标出在不同权重下都靠前的「稳健推荐」。用户用滑块或自然语言调权重，反馈同时更新画像和权重。
- **R3 多 Agent 讨论**（10–15 → 2–3 套组合，计划）：输入评分卡和用户约束。各角色先独立发言，再交叉回应 1–2 轮，主持人综合为「稳妥型 / 冲刺型 / 探索型」组合，并标注仍有分歧的点。用户旁听、插话，最后选定一套，或加约束后重新讨论。
- **R4 最终方案**（计划）：输入选定的组合。输出竞赛及理由（附证据链接）、备赛路线（每个差距对应学什么、练什么、用什么资源、达到什么里程碑）、从报名截止和比赛日倒推的时间线。用户可对路线和节奏提出修改，Agent 重新生成。

## 6. 评估方法与可信性

**证据链**
- 每个云端会话开启录制（persistent），每条数据记录 session ID、来源 URL 和读取时间。
- Lexmount 控制台可回放会话；Demo 录屏引用对应会话。
- 每轮的输入、输出和用户反馈写入会话日志，供复查。

**检验（计划）**
- **抽检**：公开信息补全后，人工抽检 30 条，逐条与来源页面比对，记录错误。
- **分档检查**：用 3 份虚构画像（编程强、数学强、零基础）检查评分卡的档位是否合理；硬性排除只依据明确冲突。
- **真实用户试用**：3–5 位同学试用，对比他们自己的判断，记录分歧和修正。
- **如实记录**：抽检表和试用反馈中的错误、失败和未解决的问题都保留在材料中，不做删减。

## 7. 与评分四项的对应

| 评分项 | 本项目如何体现 |
|---|---|
| 问题具体 | 对象明确（北交大在校学生），痛点具体（700 多条竞赛、校内系统访问受限、信息分散、判断成本高）。输出为可核对的推荐、路线和时间线。 |
| 过程可信 | 云端会话有 session ID 和录制回放，每条数据有来源 URL；会话日志记录每轮输入输出；抽检表和试用反馈可对照。 |
| 结果有价值 | 计划产出 2–3 套组合方案和备赛路线；以真实学生试用对比判断。试用效果待验证，不预先下结论。 |
| 做法可借鉴 | 能力分工表（采集、补全、讨论时实时核实）；分层抓取（WebFetch → 云浏览器）；「Agent 提草案、用户修正」的权重设计；规则只管硬条件；稳健性提示。 |

**适用限制**：公开信息可能不全，缺失处标「未说明」；依赖本机校内 VPN 和 Lexmount 本地隧道；只服务本人账号的只读采集；推荐结果是辅助参考，不替代学院或老师的判断。

## 8. 时间线与分工

分工：A 采集与云端，B Agent 与评分，C Demo、材料与用户测试。团队 2–3 人。

**范围优先级**：先打通 R0 → R1 → R2 → R4 主线；R3 多 Agent 讨论与插话计划在第二周接入，时间不够时先只做精简模式（支持方 + 质疑者 + 主持人）。

| 日期 | 内容 | 负责 |
|---|---|---|
| 10-14 | 决策门槛：隧道可用；弹窗登录后持久化 context 保留登录态；采到 1 页竞赛列表；云端必应搜索跑通 1 个竞赛；DeepSeek 工具调用跑通；领取 Pro、查看投稿表单 | A、B、C |
| 10-15～16 | 全量采集与去重；评分规则和画像结构 | A；B |
| 10-16～19 | 公开信息补全，人工抽检 30 条；Agent 对话流与工具 | A；B |
| 10-18～21 | 网页 Demo | C（B 协助） |

**当前进展（10-13）**
- 已跑通：Lexmount 云浏览器冒烟测试（创建会话、打开网页、关闭会话）；本地隧道开通成功。
- 已摸清：MIS 登录路径（统一身份认证 → 教务系统单点登录）、竞赛列表与详情页结构（含级别、A/B/C 类型、报名时间等字段）。

**失败兜底**
- 经隧道访问 MIS 不稳定：先用本地浏览器工具采集 MIS，云端只负责补全，并在材料中如实说明。
- 弹窗登录无法交互：改为截图验证码，由用户在终端输入答案。

## 9. 合规与边界

- 只使用本人账号访问，只读、低频；不执行报名操作。
- 登录与验证环节由用户本人在弹窗中完成，脚本不代填。
- 不使用官方代理绕过站点规则，不做自动验证码处理。
- 公开材料中对姓名等个人信息打码；负责人姓名不保存；不公开 MIS 原始数据全集。
- 用户的描述信息只发送给所用的大模型服务（DeepSeek），不对外公开。
- 待验证事项：经隧道登录与采集 MIS、WebFetch 与云浏览器 light 模式的接口和额度。
