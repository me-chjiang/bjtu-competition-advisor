北交大竞赛能力匹配 Agent

一个对话式 Agent：通过问答了解学生的能力与目标，从校内 700 多条竞赛中筛出适合的几项，并给出备赛路线和时间线。竞赛信息由 Lexmount 云浏览器采集 计划

为谁

北京交通大学在校学生，尤其是不清楚自己适合参加哪些竞赛的同学。

解决什么

竞赛信息只在校内教务系统（MIS）上，共 700 多条，分属不同学院、技能要求各不相同，学生难以判断。

产出什么

网页 Demo 计划：推荐竞赛及理由、备赛路线、可导出的时间线（.ics）。

状态标签：已完成 已跑通或已开通　计划 尚未实现　待验证 能否成立尚未确认

01问题与用户

  • 信息量大且分散：700 多条记录包含往年、多轮次、多赛区，同一竞赛会重复出现。
  • 信息难访问：MIS 只能经校内 VPN 访问，登录需要统一身份认证和验证码。
  • 判断成本高：学生需要同时看清三件事：自己的技能与竞赛要求是否匹配，参赛对目标（保研、简历、兴趣、奖金）是否有价值，时间是否冲突。
  • 目标用户：在校学生，可单人或组队参赛。

02方案总览

数据怎么来

  1. MIS 采集 计划
    用户本机连接校内 VPN，通过 Lexmount 本地隧道让云浏览器访问 MIS。用户在弹窗中手动完成登录；登录态保存到 Lexmount 持久化 context，之后并发 fork 出多个会话，遍历列表与详情页。只读，不执行报名。
  2. 云端补全 计划
    云浏览器（不经隧道）搜索竞赛名，打开官网、往届通知和获奖公示，抽取知识要求、难度证据和赛程。每条信息附来源 URL；取不到的标「未说明」。
  3. 去重与优先级
    按名称归一化得到「竞赛」实体，再筛出近期可报名的；补全顺序为近期可报名 → A/B 类 → 其余。

Agent 怎么用

  • 多轮筛选 R0–R4：每轮 Agent 给出草案，用户可修改后进入下一轮（见下节）。
  • R3 多 Agent 讨论 计划：6 个角色讨论；用户可旁听、勾选参与角色，并随时插话，插话在下一位发言前注入上下文。
  • 设计原则：权重不是固定公式，而是「Agent 提草案 → 用户修正」。规则只处理硬性条件（报名窗口、年级限制）；其余维度用「档位 + 证据 + 置信度」表示，不压缩成一个总分。

05评估方法与可信性

证据链

  • 每个云端会话开启录制（persistent），每条数据记录 session ID、来源 URL 和读取时间。
  • Lexmount 控制台可回放会话；Demo 录屏引用对应会话。
  • 每轮的输入、输出和用户反馈写入会话日志，供复查。

检验 计划

  • 抽检：公开信息补全后，人工抽检 30 条，逐条与来源页面比对，记录错误。
  • 分档检查：用 3 份虚构画像（编程强、数学强、零基础）检查评分卡的档位是否合理；硬性排除只依据明确冲突。
  • 真实用户试用：3–5 位同学试用，对比他们自己的判断，记录分歧和修正。
  • 如实记录：抽检表和试用反馈中的错误、失败和未解决的问题都保留在材料中，不做删减。
